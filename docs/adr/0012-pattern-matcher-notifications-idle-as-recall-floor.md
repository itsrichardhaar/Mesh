# Pattern-matcher notifications: idle is the recall floor, matchers fire first

v9 adds `approval` and `complete` Notification kinds by pattern-matching a live Pty Tab's TUI output. ADR-0006 deferred this and described matchers as label-refining *upgrades* to an already-fired idle notification ("the idle detector remains the load-bearing trigger"). Taken literally, that means an `approval` prompt — where Claude is blocked on the user *right now* — could not surface until the 8-second idle timer elapsed, which defeats the subtype's whole purpose. So v9 reinterprets the ADR-0006 invariant: a pattern matcher **creates the notification immediately** with the correct `kind` the moment it recognizes a settled screen; the idle detector is the **recall floor**, not the gate — if no matcher fires within 8s of silence, idle fires its generic `'idle'` as before. The two are deduped per idle period (whichever trips first wins; the other disarms), so a single silence never double-fires.

## Considered Options

- **Strict ADR-0006 reading — matchers only relabel an idle notification.** Rejected: forces the full 8-second delay onto `approval`/`question`, the exact latency the subtype exists to eliminate. Fine for `complete`, fatal for "Claude needs you now."
- **Per-kind timing** (`approval` fires immediately, `complete` waits for idle confirmation). Rejected: a per-kind timing matrix for no real gain — fire-first-with-idle-floor already yields the right behavior for every kind through one code path.
- **Matchers as the sole trigger** (drop the idle floor). Rejected outright: this is the failure ADR-0006 forbids. A broken matcher (Claude Code TUI change) would then *silently swallow* notifications. Idle must stay as the guaranteed floor.

## Consequences

- **The load-bearing invariant is preserved, just relocated.** ADR-0006 cared that "a broken matcher can never silently swallow a notification." That still holds: matchers add speed + precision; idle guarantees recall. Worst case on matcher breakage is a *generic* `idle` notification 8s late — never nothing. This self-heal-to-`idle` is v9's explicit safety contract.
- **Matchers read a debounced, ANSI-stripped screen snapshot**, not the raw `pty.onData` chunk stream — the source is a full-screen Ink TUI that repaints continuously. A headless terminal buffer (`@xterm/headless`, sibling of the `@xterm/xterm` the renderer already uses) maintains the current screen; matchers run against the *settled* frame (~150–300ms after the last chunk). This isolates all ANSI/repaint brittleness in one decode layer and makes each matcher a pure `(screenText) => kind | null` function — unit-tested by replaying recorded byte-stream fixtures, no Electron.
- **Anchor on structure, not prose.** `approval` matches the numbered-option-menu scaffold (the `❯` selector + `1. Yes` / `No, and tell Claude…` skeleton); `complete` matches empty-input-prompt-present + spinner-absent. Structure survives Claude Code copy changes; wording does not.
- **No schema change.** `kind` stays plain TEXT (ADR-0006); `NotificationKind` stays an open union. Adding `approval`/`complete` — and later `question` — is a code change only. The renderer still falls back to `'idle'` rendering for unknown kinds.
- **Scope boundary.** v9 is notification subtypes only. The `--timeline-*` tokens staged in v6 belong to a *separate* future feature (a live tool-activity timeline: thinking/grep/read/edit/done), not to notification kinds — they are not v9's color source. v9's kinds get their own shape-first icons (per the reduced-color-vision constraint) with color as a secondary cue.
