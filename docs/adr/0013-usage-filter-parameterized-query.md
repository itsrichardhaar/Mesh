# Usage Filter re-scopes via parameterized main-process queries, not client-side folding

v10 adds a Usage Filter (a Timeframe and a Project selector) that re-scopes the filtered Usage views — Trend, Token Composition, By-model, and the Sessions table. Those views' underlying aggregates (`byModel`, `byProject`, `topSessions`, and even the per-day `days[]` series) are pre-aggregated **across all projects** in main; the renderer's existing client-side folding (`bucketTrend`, `tokenComposition`) works off `days[]`, which has **no project or model dimension**. Rather than ship a granular per-`(day, project, model, tier)` cube plus the full session list to the renderer and re-aggregate there, **the renderer sends `{ timeframe, project }` to a parameterized `usage:get-dashboard` and main re-runs its aggregation queries with `WHERE timestamp BETWEEN … AND encoded_path = …`, returning an already-scoped dashboard.** The `Tokens|Cost` toggle and the Trend granularity (Day/Week/Month) stay **client-side** (both metrics and all granularities are present in the returned scoped `days[]`), so only Project/Timeframe changes trigger a re-fetch.

## Considered Options

- **Fat-payload client-side filtering** — main returns a granular cube + every session once; the renderer re-aggregates for any filter combo. Rejected: unbounded payload (the session list especially — capped at top-N today; a heavy account has hundreds–thousands), and it duplicates in the renderer the aggregation logic that already lives in main. Instant filter response was its only real win, and Project/Timeframe changes are infrequent relative to the metric toggle (which we keep client-side anyway).
- **Parameterized main query (chosen)** — filtering is a `WHERE` clause on the SQLite cache, the data's natural home. Bounded payloads (`LIMIT` on sessions), one aggregation code path, and it matches how `byProject`/`byModel`/`topSessions` are already computed — we add predicates, not a parallel aggregator. Cost: an async round-trip per Project/Timeframe change, which is sub-millisecond on the in-process indexed cache.

## Consequences

- **No schema change, no new migration.** The existing indices from `0006_usage_events.sql` — `idx_usage_events_time (timestamp)` and `idx_usage_events_project (encoded_path)` — already cover the filter predicates. This does **not** reopen ADR-0009: we are still reading the rebuildable cache, only with predicates.
- **Two data paths, deliberately.** (1) A **filtered** path drives Trend / Composition / By-model / Sessions from the parameterized query. (2) An **always-global** path drives the four top **Metric Cards** (Today / 7-day / This-month / Subscription Utilization) and the **Activity Heatmap** — these ignore the Usage Filter by design. The metric cards are additionally computed on the **user's local calendar day** (in main), unlike the rest of the UTC-keyed `days[]` pipeline, because "today"/"this month" must match the user's wall clock; retro-fitting local-tz to the whole pipeline is out of scope for v10.
- **By-project is hidden when a specific Project is selected** — the view *is* that project, so a by-project breakdown would be a single 100% row. By-model stays (now scoped to that project).
- **Client-side interactions stay instant.** `Tokens|Cost` and granularity never re-fetch; only Project/Timeframe do, debounced. The frequent interaction (metric toggle) has zero latency.
- **Reversible-ish but load-bearing.** This defines the Usage fetch contract. Moving to the fat-payload model later would mean re-shaping the IPC payload and adding a renderer aggregator — a real but contained change.
