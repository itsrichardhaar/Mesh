# OpenAI ships as second functional Provider; Active Provider is a global setting

[ADR-0003](./0003-provider-abstraction-claude-only-v1.md) introduced a `ModelClient` abstraction with three Provider slots (`Claude` / `OpenAI` / `Local`), shipping only `ClaudeClient` functional and the others as stubs. v4 honors that promise: `OpenAIClient` becomes a real implementation, Active Provider becomes a globally switchable setting (`active_provider`), and the orchestrator picks its client at Analyze time. `LocalClient` stays a stub for now. ADR-0003's "abstraction in code" decision remains in force and is now validated by a second functional implementation lighting it up.

## Considered Options

- **Function calling instead of Native Structured Outputs** (1:1 mirror of Claude's `tool_use` shape) — rejected: the `ModelClient` interface already abstracts the wire-level mechanism, so mirroring is unnecessary and has roughly twice the surface area. `response_format: { type: 'json_schema', strict: true }` is a single parameter; OpenAI guarantees schema conformance at decode time. Tool calling adds `tools[].function`, `tool_choice` forcing, and response parsing to find the function-call block — none of that buys us anything the interface doesn't already abstract.
- **Per-Project or per-Analysis Active Provider** — rejected for v4: no concrete demand to differentiate Providers per Project, and a per-Analysis picker pollutes the Analyze bar with a control most users would set once and never touch. Global default is the simpler primitive to layer per-Project or per-Analysis overrides on top of later if real demand emerges.
- **Reasoning models (o-series) in the catalog** — rejected: Mesh's Analysis task is summarization + extraction, not deep reasoning. Reasoning models are slow, expensive, and their Native Structured Outputs support has historically been less consistent than non-reasoning chat models, which would force per-model caveats in the catalog. If reasoning ever becomes useful for Analyses, that's a feature-level addition, not a model-tier change.
- **Click-pill switching vs Settings radio + confirm dialog** — chose click-pill: the pills already telegraph the multi-Provider UX; clicking-to-activate is the natural extension. Switching is reversible (no destruction), per-Analysis attribution is already stored in `analyses.provider`. A confirm dialog would be friction without justification.

## Consequences

- **Active Provider is global** — exactly one Provider is Active at a time across the whole app (matches `CONTEXT.md`'s definition). Stored in `settings.active_provider`; defaults to `'claude'` when absent (backward-compatible with v0.3.x installs).
- **Orchestrator instantiates its `ModelClient` at Analyze time via a factory** that reads `active_provider`, reads the selected Model from `model:{provider}`, loads the stored API key via the existing safeStorage flow, and returns `ClaudeClient` or `OpenAIClient`. The orchestrator no longer hardcodes Claude. Existing tests that pass a client directly still work — the factory is additive.
- **Prompt decoupling** — the orchestrator's `SYSTEM_PROMPT` is now Provider-agnostic. Each client appends its own output-format suffix (`CLAUDE_OUTPUT_FORMAT_SUFFIX` speaks `tool_use`; `OPENAI_OUTPUT_FORMAT_SUFFIX` speaks Native Structured Outputs). An inline snapshot test in `tests/model-clients.test.ts` pins the byte-identical Claude wire prompt so future SYSTEM_PROMPT edits can't silently change Claude's payload.
- **Catalog is 3-tier non-reasoning, mirroring Claude's pattern**: `gpt-4o-mini` (recommended default, `fast & cheap`), `gpt-4o` (`balanced`), `gpt-4-turbo` (`most capable, most $$`). `approxCostPerAnalysisUSD` values computed against current OpenAI pricing on the day of implementation — not load-bearing in this ADR.
- **Pill state is a single boolean source of truth**: `descriptor.available && hasStoredKey`. Disabled tooltip varies by reason (`comingSoonNote` for unavailable Providers like Local; `'Add an [Anthropic | OpenAI] API key in Settings → Model'` for available-but-unkeyed). Validation state is softer — a stored-but-stale key still allows the pill click; Analyze surfaces the validation error via the existing Slice 12 path.
- **Settings → Model is the single onboarding + switching surface.** Both Claude and OpenAI key fields render side-by-side (per-Provider sections); each has its own validation banner; the pill row above reflects ready-to-activate state.
- **`LocalClient` stays a stub**, gated by `available: false`. Functional Local is a candidate for v5+ if demand emerges. No code path in v4 instantiates it.
- **ADR-0003 remains in force.** Its core decision (provider abstraction in code; `analyses.provider` + `analyses.model` columns for historical attribution; disabled-pill affordance as the contract for "not available") survives unchanged. v4 only retires its "Claude-only" framing — the abstraction itself is exactly what made v4 possible without refactoring.
