# In-window notifications surface

Mesh v5 introduces a persistent notification subsystem so users can spot live agent work from anywhere in the app and never miss the moment an agent goes idle while a Pty Tab is open. The subsystem is **in-window only** — Mesh never calls `new Notification(...)` and never asks for system-level notification permissions on macOS. Notifications appear as top-right toasts inside Mesh's window and as rows in a bell-icon dropdown modeled after macOS's Notification Center. The toast subscribes to a `notifications:created` event channel; the dropdown reads from a SQLite `notifications` table with 7-day retention. Mute controls suppress the *toast event*, not the *storage* — paused notifications still accumulate in the dropdown so the user can review what they missed when they unmute.

## Considered Options

- **System-level macOS notifications** via `new Notification(title, options)` from the renderer — rejected: introduces a permission flow at first launch (deny vs allow), depends on system-level Do Not Disturb / Focus mode state Mesh has no visibility into, and the user must have macOS's notification UI open or be looking at the corner of their screen to see them. In-window keeps the surface scoped to "when Mesh is the foreground app," which is when the user can act anyway. If a real demand for system-level alerts emerges (e.g., users running Mesh minimized behind a long-running agent), it can layer on top of the in-window subsystem without rework.
- **Pattern-match Claude Code's TUI to subtype notifications** (`approval` / `complete` / `question` at v5 ship time) — rejected for v5, deferred to a future slice: parsing the TUI is brittle (every Claude Code TUI update could silently break detection), false negatives are invisible (you don't know when you missed a prompt), and the testing matrix grows with each pattern. The idle-transition primitive is the same `lastActivityAt` machinery the spinner already uses — 100% recall (if Claude stopped writing, Mesh noticed), zero coupling to a specific output format. Pattern matchers can land later as *upgrades*: they refine the label (`'idle'` → `'approval needed'`) when they fire, but the idle detector remains the load-bearing trigger so a broken pattern matcher can never silently swallow a notification.
- **`CHECK`-constrained `kind` enum in SQLite** — rejected: every new notification subtype would need a migration. Storing `kind` as plain TEXT lets future subtypes be a code change. The renderer treats unknown kinds as `'idle'` for graceful degradation, so a forward-rolling deployment never breaks.
- **One global mute toggle only** — rejected: a noisy long-running script in Project X shouldn't force the user to choose between "all toasts on" and "all toasts off." Per-Project mute is the smallest set that handles "I want focus on Project A but Project B keeps notifying me."
- **Per-notification-type mute** (separate switches for idle / approval / complete) — rejected for v5: only one type ships in v5, so granularity over a one-element taxonomy is premature surface area. Adds when the taxonomy grows.
- **Do-Not-Disturb time windows** (quiet hours) — rejected for v5: cron-like config surface for a need that hasn't actually emerged. Foreground suppression already covers the "I'm not at my desk" case. Can layer on later.
- **Optimistic renderer state updates** on `markRead` / `clearAll` — rejected: the renderer treats itself as a cache over main's authoritative SQLite. Every action calls the IPC and waits for main's update event to refresh local state. Slightly higher latency than optimistic; zero chance of the UI showing state that didn't persist.

## Consequences

- **`notifications` table** (`id` UUID PK, `created_at` ISO 8601, `encoded_path`, `session_id`, `pty_id` nullable, `kind` TEXT, `label_text`, `read_at` nullable) carries one row per fired notification. Indexes: `idx_notifications_recent` for the newest-first list query, and a partial `idx_notifications_unread` over unread rows for fast unread-badge + dropdown ordering. Migration `0004_notifications.sql`.
- **Idle detector** in `src/main/notifications/idle-detector.ts` watches each live Pty Tab's PTY-data stream and fires `notifications:created` events when a tab transitions to idle (no output for ≥ 8 s) **AND** is not foregrounded. Pure logic with injectable clock / scheduler / emitter / UUID factory — the timing, debounce, foreground suppression, and auto-mark-read rules are unit-testable independent of Electron.
- **Foreground suppression is total** — the user is already looking at the tab, so neither a toast event NOR a SQLite row is created. Mute is different (see below): mute suppresses the toast but preserves the row.
- **Debounce: one notification per idle period.** The fire timer is cancelled by any `onPtyData(ptyId)` chunk and re-armed; once a notification has fired, the trigger disarms until activity resumes or the PTY exits. A single overnight idle generates one notification, not dozens.
- **Auto-mark-read** triggers without renderer action when:
  - The PTY emits new output after a notification fired (agent un-idled — the wait condition is gone), or
  - The PTY exits (process ended — no action possible).
  - Plus the renderer-driven case: the user navigates to a Session's Pty Tab via any means (Workspace tab click, "Jump to session" button, dropdown row). All scoped via `markAllRead({ sessionId })` so only that session's unread rows clear.
- **IPC surface** is a single `notifications.*` namespace: `list`, `markRead(id)`, `markAllRead(opts?)`, `clearAll(opts?)`, `setForegroundPty(ptyId | null)`, `getGlobalMute`, `setGlobalMute(value)`, `getProjectMute(encodedPath)`. Per-Project mute writes go through the existing `projects.update(encodedPath, { muteNotifications })` IPC — no separate notifications setter. Event channels: `notifications:created` (full row payload so toast can render without a round-trip), `notifications:updated` (`{ ids: string[] }`), `notifications:cleared` (`{ encodedPath: string | null }`), `notifications:mute-changed` (`{ scope: 'global' | 'project', value: boolean, encodedPath? }`).
- **Mute gates toast emission, not storage.** When `notifications_global_mute === true` OR `isProjectMuted(encodedPath) === true`, the row still persists to SQLite (the dropdown shows it, the unread badge appears on the bell) but the `notifications:created` event is suppressed. The user can review what they missed by opening the dropdown. Matches macOS DND behavior.
- **Bell icon swaps `Bell` → `BellOff`** in the top bar when global mute is on. The unread dot still appears so the user can tell new things landed while muted; the icon's title attribute clarifies the state.
- **`useLiveSessions` is the foundation v5 indicators read from.** v5's "subtle green + spinner" UX on the Session row, Project sidebar, ProjectCards tile, and Project Detail header all consume the same App-level registry. The notification subsystem and the indicator subsystem share the activity primitive but otherwise live in parallel: indicators have no persistence layer; notifications have no spinner.
- **7-day retention sweep on app boot.** `DELETE FROM notifications WHERE created_at < (now - 7 days)` runs once in `whenReady` so the table stays small without user housekeeping. No user-facing retention setting in v5.
- **Future kinds plug in here.** When pattern-matching detectors land (a future slice), they emit `'approval'` / `'complete'` / `'question'` etc. into the existing `kind` column. The renderer's row + toast components render `label_text` directly (no kind-driven branching today), so adding a kind is a code change with zero schema impact. The UI can optionally light up kind-specific icons/styling in a future polish without breaking the v5 baseline.
- **Future signal sources plug in here too.** When v6's Scheduled Analysis lands, the orchestrator's "scheduled run completed" event becomes another `notifications:created` payload — same table, same dropdown, same toast. v5 deliberately designed the surface to receive more signal sources than just idle detection.

## Update — 2026-06-30

Recorded at v5 ship. Idle detection's 8-second threshold + the "no silent misses" rationale was validated during HITL dogfood: notifications fired reliably for genuine idle periods and the foreground-suppression rule prevented every "I was already looking at it" false-positive in real usage. The pattern-matching upgrades (Q2's hybrid completion) remain explicitly deferred — they're the natural next iteration of the surface this ADR introduces, not a deficiency of the baseline.
